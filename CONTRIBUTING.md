# Contributing to Glyph

Preserve one entry point with focused references. Propose changes based on concrete tasks and observed output; explain what the guidance improves and when it should be broken. A small reversible correction does not need a separate approval ceremony.

## Rule format

Keep useful fields: Confidence Level, Purpose, Reasoning, Constraint, Bad/Good examples and Exceptions. Use **Requirement** for correctness/accessibility obligations, **Pattern** for adaptable starting points, and **Taste hypothesis** for design judgment. Do not label taste as high-confidence evidence. Link authoritative evidence when making an empirical claim and state its scope.

## Change process

1. Inspect the relevant product task, current guidance and overlapping references.
2. Resolve contradictions instead of adding a parallel rule system.
3. Edit canonical files in `skills/glyph/`; keep root compatibility pointers valid.
4. Update the entry's selective-load table for a new reference and retain required license notices.
5. Regenerate docs source, check every relative reference and test a disposable bundle copy.
6. For behavioral changes, use fixed briefs and comparable model/content/assets/iteration budgets. Record failures, revisions and unperformed checks; do not fabricate outcomes.

Keep PRs focused. Include concrete prompt/output evidence when available, actual validation and limitations. Do not impose the Glyph website's fonts, colors, hero or logo on every generated product. Check rights before adapting text/code/assets and preserve attribution.

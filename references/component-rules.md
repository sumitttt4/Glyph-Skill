# Component Rules

This module defines rules for functional components generated by AI coding assistants, specifying how they behave, look, and organize data.

---

### Navigation
* **Confidence Level**: Critical
* **Purpose**: Structure predictable top-level routes and clear brand markers.
* **Reasoning**: Cluttered header layouts with vague link lists disorient users.
* **Constraint**: Navigation headers must have a sticky height of `60px`–`72px`, a bottom border (`1px` solid, low contrast), a left-aligned logo, center-aligned nav items (max 5 links), and a right-aligned action button. Nav layers must be restricted to a maximum of 2 hierarchy levels.
* **Example**:
  * **Bad**: A top header with 12 loose links, no logo, and 3 buttons competing on the right.
  * **Good**: A sticky header with a left logo, links to "Rules, Docs, Install," and a primary "Install" CTA on the right.
* **Exceptions**: Dashboard sub-menus or landing pages with simple one-page scrolling tags.

---

### Forms
* **Confidence Level**: Critical
* **Purpose**: Enforce logical, accessible data entry and input focus states.
* **Reasoning**: Inline labels and missing validation markers cause form abandonments and validation errors.
* **Constraint**: Standard input labels must be placed directly above input fields. Group elements vertically using a single column structure.
* **Example**:
  * **Bad**: Placing label placeholders inside fields with no outer text, making it impossible to see what the input is once typed.
  * **Good**: Place field labels in bold text (`text-xs font-semibold`) above input boxes (`height: 40px`, `radius: 8px`), adding a red asterisk for required values.
* **Exceptions**: Single-line newsletter sign-ups.

---

### Authentication
* **Confidence Level**: Recommended
* **Purpose**: Simplify entry screens to boost conversion rates.
* **Reasoning**: Auth screens with complex visual sidebars distract the user from entering their credentials.
* **Constraint**: Center sign-in forms inside a single-column container (`max-w-[400px]`), placing social integrations as primary buttons on top, separated from credential fields by a gray line.
* **Example**:
  * **Bad**: Styling sign-in screens with floating decorations, custom grids, and side-by-side columns.
  * **Good**: A centered card with standard fields and a single full-width primary "Continue" button.
* **Exceptions**: None.

---

### Settings
* **Confidence Level**: Recommended
* **Purpose**: Layout configuration matrices cleanly for easy editing.
* **Reasoning**: Settings screens with random layouts make finding settings frustrating.
* **Constraint**: Group configurations into cards separated by category, using a left sidebar menu to jump between tabs.
* **Example**:
  * **Bad**: A single long form list with 30 miscellaneous check controls and text inputs in a row.
  * **Good**: Group settings into distinct cards (e.g., "Profile Settings," "Security Settings") with a sticky navigation sidebar on the left.
* **Exceptions**: Mobile settings grids.

---

### Dashboards
* **Confidence Level**: Critical
* **Purpose**: Enforce high-level data clarity for analytics.
* **Reasoning**: Dashboards with neon graphs, custom widgets, and unlabelled charts fail to deliver real-time insights.
* **Constraint**: Use a top metric row with exactly 3 to 4 cards showing primary values, placing details and charts directly below.
* **Example**:
  * **Bad**: A dashboard hero showing a huge neon chart, multiple floating card groups, and no metric summary numbers.
  * **Good**: A top row of 4 KPI cards (e.g., "Total Revenue," "Active Users") followed by a simple line chart.
* **Exceptions**: Log viewers.

---

### Tables
* **Confidence Level**: Critical
* **Purpose**: Keep tabular data readable and sortable.
* **Reasoning**: Mixing multiple font weights and wrapping text lines inside compact rows makes tables unreadable.
* **Constraint**: Tables must apply `table-layout: auto`, a horizontal scroll overlay for mobile viewports, monospaced fonts for numerical metrics, and prevent text wrapping in cell headings.
* **Example**:
  * **Bad**: Setting table numbers to standard body fonts with no alignment, letting columns overlap on smaller viewports.
  * **Good**: Align column metrics to the right, use monospace fonts (`font-mono`) for numerical values, and wrap tables in a container with horizontal scroll support.
* **Exceptions**: Text-heavy document logs.

---

### Pricing
* **Confidence Level**: Critical
* **Purpose**: Highlight value choices clearly.
* **Reasoning**: Visually identical pricing cards make it hard for users to decide which plan is best.
* **Constraint**: Arrange pricing cards in a grid (max 3 plans), visually elevating the featured plan with a subtle border highlight, badge, and primary colored button.
* **Example**:
  * **Bad**: A pricing section with three identical cards using the same border style and white buttons.
  * **Good**: Elevate the center "Pro" plan by adding a border (`border-[#072ca8]`), a "Most Popular" tag, and a solid blue button, while other cards use border buttons.
* **Exceptions**: Tiered pricing sliders.

---

### Cards
* **Confidence Level**: Recommended
* **Purpose**: Package group elements consistently.
* **Reasoning**: Cards with varying paddings and content arrangements look uncoordinated.
* **Constraint**: Card wrappers must use a `12px` border-radius, a `24px` inner padding, an icon inside a soft background container in the top-left, a small uppercase category tag, and left-aligned text copy.
* **Example**:
  * **Bad**: A card with a centered header, a left-aligned paragraph, and no margins.
  * **Good**: A structured card with a top-left icon, an uppercase tag (`font-bold uppercase tracking-wider text-[10px]`), a semibold heading, and a regular description.
* **Exceptions**: Bento grid visual containers.

---

### Search
* **Confidence Level**: Critical
* **Purpose**: Give immediate search feedback.
* **Reasoning**: Small, hidden search icons force users to search for the search function itself.
* **Constraint**: Search inputs must remain persistent and visible in headers or sidebars, incorporating a search icon in the left margin and a clear keyboard shortcut hint (e.g., `Cmd + K`).
* **Example**:
  * **Bad**: A header that requires clicking a small magnifying glass icon to expand an input box.
  * **Good**: A permanent input field with a search icon on the left and a light gray keyboard badge on the right.
* **Exceptions**: Mobile views where search collapses into a header overlay.

---

### Command Palette
* **Confidence Level**: Recommended
* **Purpose**: Speed up user actions using a keyboard launcher.
* **Reasoning**: Palettes with no keyboard support are just glorified dropdowns.
* **Constraint**: Keep overlay panels centered (`max-w-[600px]`), trap focus inside the modal, highlight active lines on mouse hover or arrow keys, and list shortcut keys on the right.
* **Example**:
  * **Bad**: A command palette that requires using the mouse to click option rows.
  * **Good**: Let users navigate command palettes with the arrow keys, trigger actions with Enter, and exit the menu with Esc.
* **Exceptions**: Mobile viewports.

---

### Modals & Dialogs
* **Confidence Level**: Critical
* **Purpose**: Present focused actions without losing page context.
* **Reasoning**: Modals without distinct close buttons or dim backdrops trap users on the screen.
* **Constraint**: Modals must sit on a semi-transparent dark backdrop (`bg-black/50` or `bg-black/60`), trap focus when active, close on `Esc` key press, and provide a clear close button in the top-right.
* **Example**:
  * **Bad**: A white modal container rendered on a white background with no backdrop dimming or close icon.
  * **Good**: Centering a modal container over a dimmed backdrop (`backdrop-blur-sm bg-black/40`), complete with a top-right close button.
* **Exceptions**: Toast alerts.

---

### Empty States
* **Confidence Level**: Recommended
* **Purpose**: Guide users when no content exists yet.
* **Reasoning**: Blank dashboard screens look broken and leave users confused on next steps.
* **Constraint**: Empty containers must display a single icon or illustration, a short header, a descriptive explanation, and a primary action button below to create a resource.
* **Example**:
  * **Bad**: Showing a completely blank screen inside a dashboard table with no text or buttons.
  * **Good**: A centered card showing a file icon, a "No documents yet" header, a description, and a button to "Create Document."
* **Exceptions**: Sub-panels or inline widgets.

---

### Loading & Skeletons
* **Confidence Level**: Recommended
* **Purpose**: Keep the layout stable while content load compiles.
* **Reasoning**: Spinning loading wheels cause layout shifts once content compiles.
* **Constraint**: Place placeholder skeletons matching the shape of target components, using a pulse animation (cycling opacity between `0.4` and `0.85` every `1.5s`).
* **Example**:
  * **Bad**: Using a large spinning loading wheel that shifts elements once content loads.
  * **Good**: Render light gray boxes that match the height and width of card text lines while data loads.
* **Exceptions**: Tiny loading icons on buttons.

---

### Errors & Alerts
* **Confidence Level**: Critical
* **Purpose**: Deliver clear error messages.
* **Reasoning**: Generic error alerts do not tell users how to recover.
* **Constraint**: Place alert boxes in high-contrast red/yellow containers with standard icons, placing a secondary retry action button inside the panel.
* **Example**:
  * **Bad**: Displaying a green success-style box containing the text "Error saving changes" in small font.
  * **Good**: A light red container (`bg-red-50 border-red-200`) with a red warning icon, an error description, and a "Retry" button.
* **Exceptions**: None.

---

### Success Messages
* **Confidence Level**: Recommended
* **Purpose**: Confirm successful user actions.
* **Reasoning**: Missing success feedback forces users to click trigger buttons repeatedly, causing duplicate submissions.
* **Constraint**: Display success states using a check icon (`lucide/CheckCircle`) in green, a clear confirmation title, and a next-step action link.
* **Example**:
  * **Bad**: Keeping a form active after submission with no visual feedback.
  * **Good**: Swapping a form with a card showing a green check icon, a "Project created" heading, and a button to "View Dashboard."
* **Exceptions**: Toast notifications.

---

### Pagination
* **Confidence Level**: Recommended
* **Purpose**: Navigate multi-page data lists.
* **Reasoning**: Endless scrolls or pagination without page numbers make locating items difficult.
* **Constraint**: Render pagination as a centered horizontal row of numbers, disabling the "Prev" and "Next" buttons at the edge gates.
* **Example**:
  * **Bad**: A pagination bar that lets users click "Previous" when on the first page, causing error pages.
  * **Good**: A centered row showing pages `[1] [2] [3]`, graying out the "Previous" arrow when on page 1.
* **Exceptions**: Infinite scroll grids.

---

### Filters
* **Confidence Level**: Recommended
* **Purpose**: Refine dashboard search results.
* **Reasoning**: Hidden, complex filter modals make refining lists slow.
* **Constraint**: Render filter controls inline as clickable tabs or toggle pills, incorporating a visible "Clear All" button.
* **Example**:
  * **Bad**: Requiring users to open a nested multi-level modal to filter results by a single category.
  * **Good**: Horizontal toggle pills (e.g., "All," "Active," "Completed") placed directly above the list layout.
* **Exceptions**: Complex multi-variable queries in developer logs.

---

### Charts & Graphs
* **Confidence Level**: Critical
* **Purpose**: Represent data trends clearly.
* **Reasoning**: Colorful charts with missing labels and legend keys fail to inform.
* **Constraint**: Restrict chart keys to a maximum of 3 colors (using shades of the brand color first), apply hover tooltips showing exact values, and label all axes.
* **Example**:
  * **Bad**: A bar chart using 8 different bright colors with no labels or hover states.
  * **Good**: A single color area chart (`#072ca8` gradient) with a tooltip overlay that displays coordinates on hover.
* **Exceptions**: Complex data maps.

---

### Documentation
* **Confidence Level**: Critical
* **Purpose**: Keep documentation easily readable.
* **Reasoning**: Long, flat docs pages force users to scroll endlessly to find simple details.
* **Constraint**: Docs pages must use a sticky navigation sidebar on the left, a main content reading column restricted to `720px`, and a table of contents sidebar on the right.
* **Example**:
  * **Bad**: A single centered text page with no sidebars and a full-screen line length.
  * **Good**: A 3-column layout with a left sidebar, centered markdown content (`max-w-[720px]`), and a right-aligned section links index.
* **Exceptions**: Simple README pages.

---

### Developer Tools
* **Confidence Level**: Recommended
* **Purpose**: Make API integration fast.
* **Reasoning**: Unformatted code snippets are hard to read and scan.
* **Constraint**: Enforce monospace formatting, include a standard syntax highlighter layout, and add a "Copy Code" button in the top-right corner.
* **Example**:
  * **Bad**: Rendering raw terminal snippets inside standard body font wrappers.
  * **Good**: Use a dark code box with a header showing the tool name, syntax-highlighted lines, and a copy button.
* **Exceptions**: None.

---

### Glassmorphic Panels
* **Confidence Level**: Recommended
* **Purpose**: Layer floating statistics widgets on top of abstract graphic backdrops with high legibility.
* **Reasoning**: Plain gray inputs look muddy over rich image backgrounds. Blurring coordinates separates the card layer cleanly without blocking the backdrop depth.
* **Constraint**: Overlays must use translucent backgrounds (e.g. `bg-white/10` or `bg-white/20`), a blur filter (`backdrop-blur-md` or `backdrop-blur-lg`), and double outlines: a white-translucent top border (`border-white/30`) and a dark-translucent bottom border or shadow.
* **Example**:
  * **Bad**: Placing solid, flat grey boxes on top of a dynamic blue/purple liquid graphic.
  * **Good**: Overlaying a card styled with `backdrop-blur-lg bg-white/15 border border-white/25 shadow-xl`.
* **Exceptions**: Dashboard log tables.

---

### Review Slider Cards
* **Confidence Level**: Critical
* **Purpose**: Present customer reviews and highlight stats in a structured carousel.
* **Reasoning**: Flat, stacked columns of reviews make pages look long and unconsidered. Creating structured slider elements breaks horizontal grids.
* **Constraint**: Review cards must wrap in a horizontal flex layout, containing a user avatar circle (`40px`), full name, rating stars (`lucide/Star` in gold `#F59E0B`), and a clear outcome tag (e.g. "Save 15%").
* **Example**:
  * **Bad**: Displaying reviews in a long, centered vertical paragraph column under the hero.
  * **Good**: Wrapping review cards inside a scroll container (`flex overflow-x-auto gap-4 scrollbar-none`) containing structured reviews.
* **Exceptions**: Standalone hero callouts.

---

### Product Spec & Quantity Selectors
* **Confidence Level**: Critical
* **Purpose**: Style transaction options inline with Shopify and e-commerce standards.
* **Reasoning**: Scattered input fields and generic dropdown choices look amateurish and lower purchase conversion.
* **Constraint**: Quantity controls must bundle selectors inline, using vertical stack lists for packs (e.g., "1 Pack", "2 Packs") with highlighted borders and explicit price targets.
* **Example**:
  * **Bad**: Using a generic input field for quantities with no default choices or pricing details.
  * **Good**: Render a structured card list where the active option is highlighted with a brand border (`border-[#072ca8]`) and displays the unit price and savings amount right-aligned.
* **Exceptions**: B2B enterprise procurement forms.

---

### Dashboard Tooltips & Coordinate Guides
* **Confidence Level**: Recommended
* **Purpose**: Provide precise data point inspection on dashboard charts.
* **Reasoning**: Plain graphs without hover indicators force users to guess exact coordinate values.
* **Constraint**: Charts must project a vertical dashed line guide (`border-dashed border-gray-300`) tracking the mouse pointer, displaying a floating tooltip container containing the key metric and date values.
* **Example**:
  * **Bad**: Showing a static line chart where hovering over coordinates has no visual response or text changes.
  * **Good**: Placing a vertical hover tracking bar that updates a floating absolute panel showing `Oct 15, 2026: 75%`.
* **Exceptions**: Tiny sparkline analytics.

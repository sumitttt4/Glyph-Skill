# Core Color Rules

This module defines rules for functional color usage across layouts generated by AI coding assistants.

---

### Category Visual Intent
* **Confidence Level**: Critical
* **Purpose**: Match product color schemes to their industry category and target audience trust expectations.
* **Reasoning**: Generic startup gradients or neon colors dilute trust and look amateurish in professional applications.
* **Constraint**: Schemes must map to specific industry targets.
  - *Fintech/Security*: Deep navy/slate base, cobalt or teal accents.
  - *Healthcare/Wellness*: Low-contrast soft green, calm blue, warm white bases. No aggressive highlights.
  - *DevTools/AI Infra*: Dark-first charcoal base, monospaced typography, single bright green or blue terminal accent.
  - *Productivity/B2B SaaS*: Clean white/soft gray base, single dark blue or dark orange action accent.
* **Example**:
  * **Bad**: Styling a banking app hero with a hot pink to neon purple linear gradient background.
  * **Good**: Styling a banking app with a light slate gray background (`#F8F9FB`), primary text (`#0F1923`), and a single cobalt accent (`#2563EB`) on CTAs.
* **Exceptions**: None.

---

### Max Text Colors Per Surface
* **Confidence Level**: Critical
* **Purpose**: Restrict the number of text shades inside a single container to preserve layout hierarchy.
* **Reasoning**: Multiple gray and colored fonts in one text block make scanning difficult and confuse the user.
* **Constraint**: Any card, banner, or page block must use a maximum of 2 text colors: Primary text (`#111111` or `#E2E2E2`) and Secondary/Muted text (`#666666` or `#A1A1A1`).
* **Example**:
  * **Bad**: A card containing a black heading, slate gray description, light blue link, and red warning text.
  * **Good**: A card containing a primary dark gray heading (`#111111`) and a secondary muted gray description (`#666666`).
* **Exceptions**: Code snippets (which use standard syntax highlighting) or status labels containing a single error/success keyword.

---

### Max Border Colors Per Surface
* **Confidence Level**: Critical
* **Purpose**: Standardize card and divider outlines to avoid grid noise.
* **Reasoning**: Mixing multiple light border colors makes a page feel messy and fragment-based.
* **Constraint**: Restrict every grid or layout section block to exactly 1 border color style.
* **Example**:
  * **Bad**: A form page where cards have light gray borders, inputs have dark gray borders, and active tabs have orange borders all showing at once.
  * **Good**: Standardizing all card and element outlines to `1px solid rgba(0, 0, 0, 0.08)`.
* **Exceptions**: Input focus active rings.

---

### Single Accent Focus
* **Confidence Level**: Critical
* **Purpose**: Enforce a single focal point per viewport.
* **Reasoning**: Saturated primary colors compete for user attention. If everything is colored, nothing stands out.
* **Constraint**: Maximum of 1 strong brand accent color per page view, reserved exclusively for primary calls to action or key status indicators.
* **Example**:
  * **Bad**: A page header with an orange button, orange navigation icons, orange tag alerts, and orange bullet points.
  * **Good**: Keep the entire header grayscale, and apply the accent color only to the primary "Deploy" CTA button.
* **Exceptions**: Multi-state graphs or dashboard charts where color is functional to represent data dimensions.

---

### Dark Mode Surface Hierarchy
* **Confidence Level**: Recommended
* **Purpose**: Build depth and structural division in dark mode interfaces.
* **Reasoning**: Dark products that use a single shade of black for all elements look flat and make it hard to locate active modals.
* **Constraint**: Surfaces must elevate by becoming progressively lighter.
  - Background base: `#0D0D0D`
  - Cards and panels: `#161616`
  - Modals and elevated actions: `#222222`
* **Example**:
  * **Bad**: Placing a `#0D0D0D` input field directly on top of a `#0D0D0D` card container.
  * **Good**: Placing a `#1C1C1C` button or dropdown on a `#161616` surface inside a `#0D0D0D` page layout.
* **Exceptions**: Flat interfaces that use strong, physical borders (`1px solid white/15`) to divide sections without using background offsets.

---

### Text Contrast Limits
* **Confidence Level**: Critical
* **Purpose**: Maintain readability for users with varying visual capabilities.
* **Reasoning**: Light gray text on off-white backgrounds violates access limits and causes eye strain.
* **Constraint**: All text must meet WCAG AA minimum contrast ratio (4.5:1 for body copy under 18pt, 3:1 for headers over 18pt).
* **Example**:
  * **Bad**: Styling copy using `#A1A1A1` on a background of `#FAFAF9` (contrast ratio of 2.1:1).
  * **Good**: Styling copy using `#6B6B6B` on a background of `#FAFAF9` (contrast ratio of 4.7:1).
* **Exceptions**: Disabled buttons or inactive inputs.

---

### Translucent Glassmorphic Colors
* **Confidence Level**: Recommended
* **Purpose**: Control card color transparency overlaying graphical backdrops to preserve text readability.
* **Reasoning**: Completely transparent backdrops cause text to merge with image details behind them. A minimum opacity layer is required to ensure contrast.
* **Constraint**: Translucent white panels must maintain a minimum background opacity of `10%` (`rgba(255, 255, 255, 0.1)`) up to `25%` (`rgba(255, 255, 255, 0.25)`), and translucent dark panels must maintain a minimum opacity of `70%` (`rgba(17, 17, 17, 0.7)`).
* **Example**:
  * **Bad**: Using a card with `bg-white/5` (5% opacity) over a detailed background image, making the text unreadable.
  * **Good**: Using a card with `bg-white/15` (15% opacity) and `backdrop-blur-md` to diffuse the image behind the text.
* **Exceptions**: Small visual tags or borders.
